# Лабораторна робота №6 (2 години)

**Тема:** Декомпозиція робіт (WBS) на основі користувацьких історій

Практика багаторівневої структуризації обсягу проєкту (Scope Management): систематичний перехід від користувацьких вимог (User Stories та Use Cases з Лабораторної роботи №5) до ієрархічної структури робіт (Work Breakdown Structure), перевірка "Правила 100%" та "Правила 8/80", складання Словника WBS (WBS Dictionary).

**Мета:** Навчитися трансформувати функціональні специфікації та User Stories у повну деревоподібну структуру конкретних технічних пакетів робіт (Work Packages), закріплювати інженерні зони відповідальності та формувати основу для подальшого оцінювання строків і бюджету IT-проєкту.

**Технологічний стек:** Draw.io / Miro / Lucidchart (для графічної схеми дерева WBS) + Google Docs / Microsoft Word / Excel (для словника WBS).

## Завдання

У Лабораторній роботі №5 ви сформували базу вимог для свого IT-проєкту: написали 3 деталізовані User Stories із критеріями приймання (Acceptance Criteria) у форматі Gherkin (Given-When-Then) та описали складний Use Case.

Тепер ці вимоги необхідно декомпозувати на конкретні інженерні задачі для команди розробки. Вам потрібно побудувати повну деревоподібну структуру робіт проєкту (WBS) та оформити формальний опис для кінцевих пакетів робіт.

### Перелік завдань:

1.  Побудувати графічну діаграму WBS (мінімум 3--4 рівні глибини) з прямою інтеграцією модулів та User Stories з Лабораторної №5.

2.  Провести валідацію виділених пакетів робіт (Work Packages) за "Правилом 100%" та "Правилом 8/80 годин".

3.  Скласти паспорт-словник WBS (WBS Dictionary) для двох ключових пакетів робіт різної технічної спеціалізації (наприклад, Backend API та Frontend UI).

### Перевірка правила 100%

Правило 100% означає, що дочірні елементи повністю охоплюють обсяг батьківського елемента, а разом усі гілки охоплюють погоджений обсяг проєкту.

> 1\. Кореневий елемент охоплює весь визначений обсяг: аналіз і проєктування, оплату карткою, перевірку балансу, електронний чек, тестування та запуск.
>
> 2\. Усі три історії з лабораторної №5 мають пряме відображення. Їхні сценарії також перевіряються в 1.5.
>
> 3\. Кожен компонент рівня 3 розбитий на конкретні пакети робіт рівня 4.
>
> 4\. Не додано функцій поза погодженим сценарієм.

Отже, правило 100% дотримано для визначеного обсягу MensaCard. Якщо згодом додадуть нову вимогу, її потрібно погодити й внести до WBS через контроль змін, а не непомітно додавати до наявного пакета робіт.

### Крок 2. Валідація пакетів робіт за "Правилом 8/80" {#крок-2.-валідація-пакетів-робіт-за-правилом-880}

Пакет робіт (Work Package) --- це атомарний елемент на самому низу дерева WBS:

- Робота не повинна бути надто дрібною (менше 8 годин / 1 робочого дня), інакше менеджер потоне в мікроменеджменті;

- Робота не повинна бути надто великою (понад 80 годин / 10 робочих днів), оскільки для неї неможливо точно оцінити ризики та відстежити статус виконання.

Оберіть зі створеного дерева 4 пакети робіт різного спрямування (Backend, Frontend, QA, DevOps). Для кожного вкажіть:

1.  Повний код WBS (наприклад, 1.2.1.3);

2.  Назву задачі;

3.  Приблизну планову тривалість у годинах (перевірте діапазон 8--80 годин);

4.  Призначену технічну роль виконавця.

.

| **Код WBS** | **Назва задачі** | **Тривалість** | **Роль виконавця** |
|:--:|----|----|----|
| 1.2.1.1 | Перевірити оплату та списати кошти | 24 год | Backend Developer |
| 1.3.2.2 | Показати баланс картки | 12 год | Frontend Developer |
| 1.5.1.2 | Перевірити помилкову картку й нестачу коштів | 16 год | QA Engineer |
| 1.5.2.2 | Запустити систему й перевірити її | 8 год | DevOps Engineer |

Усі чотири пакети перебувають у межах правила 8/80. DevOps-пакет оцінено рівно у 8 годин --- це мінімально прийнятна межа за обраним правилом; за появи додаткових робіт з інфраструктури його слід переоцінити або розділити на окремі пакети. Оцінки є попередніми плановими трудовитратами, а не календарною тривалістю проєкту.

## Контрольні запитання

1.  У чому полягає суть "Правила 100%" при побудові WBS та як воно запобігає розширенню меж проєкту (Scope Creep)?

Правило 100% означає, що дочірні елементи WBS повністю охоплюють обсяг робіт батьківського елемента. Воно запобігає Scope Creep, оскільки всі нові роботи потрібно погоджувати та вносити до структури через контроль змін.

2.  Чому пакети робіт (Work Packages) не рекомендується дробити менше 8 годин або об'єднувати у блоки понад 80 годин?

### Робота не повинна бути надто дрібною (менше 8 годин / 1 робочого дня), інакше менеджер потоне в мікроменеджменті; {#робота-не-повинна-бути-надто-дрібною-менше-8-годин-1-робочого-дня-інакше-менеджер-потоне-в-мікроменеджменті}

### Робота не повинна бути надто великою (понад 80 годин / 10 робочих днів), оскільки для неї неможливо точно оцінити ризики та відстежити статус виконання. {#робота-не-повинна-бути-надто-великою-понад-80-годин-10-робочих-днів-оскільки-для-неї-неможливо-точно-оцінити-ризики-та-відстежити-статус-виконання.}

### 3. Чим відрізняється дерево WBS від організаційної структури команди (OBS) та від беклогу задач у Scrum? {#чим-відрізняється-дерево-wbs-від-організаційної-структури-команди-obs-та-від-беклогу-задач-у-scrum}

### WBS описує весь обсяг робіт проєкту та його поділ на пакети робіт. OBS показує організаційну структуру команди й відповідальність учасників. Беклог Scrum --- це впорядкований список завдань і вимог, які команда поступово виконує та пріоритезує. {#wbs-описує-весь-обсяг-робіт-проєкту-та-його-поділ-на-пакети-робіт.-obs-показує-організаційну-структуру-команди-й-відповідальність-учасників.-беклог-scrum-це-впорядкований-список-завдань-і-вимог-які-команда-поступово-виконує-та-пріоритезує.}

### 4. Яку роль відіграє Словник WBS (WBS Dictionary) у врегулюванні спорів щодо приймання робіт замовником? {#яку-роль-відіграє-словник-wbs-wbs-dictionary-у-врегулюванні-спорів-щодо-приймання-робіт-замовником}

## Словник WBS чітко визначає зміст робіт, очікувані результати та критерії приймання. У разі спору замовник і виконавець можуть звірити результат із погодженими вимогами й об'єктивно визначити, чи виконано роботу. {#словник-wbs-чітко-визначає-зміст-робіт-очікувані-результати-та-критерії-приймання.-у-разі-спору-замовник-і-виконавець-можуть-звірити-результат-із-погодженими-вимогами-й-обєктивно-визначити-чи-виконано-роботу.}

## Критерії оцінювання

- Побудова багаторівневої структури WBS із дотриманням правила 100%: до 40 балів;

- Чітка прив'язка до User Stories з Лабораторної №5 та валідація правила 8/80: до 25 балів;

- Складання детального Словника WBS (WBS Dictionary) для 2 пакетів робіт: до 25 балів;

- Відповіді на контрольні запитання: до 10 балів.
